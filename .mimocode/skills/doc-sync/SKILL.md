# TGWS 文档同步技能（最优版 v2.0）

## 核心原则

### 文档职责划分

| 文档 | 职责 | 何时读取 | 何时写入 |
|------|------|----------|----------|
| **MEMORY.md** | 真实状态源 | 展示待办、进度、配置、悬停信息时 | 变更记录、待办更新 |
| **AGENTS.md** | 规则约束源 | 查阅开发约束、架构、工具使用规则时 | 新增规则、教训记录 |
| **PRD** | 设计权威源 | 查阅功能需求、设计规范时 | 功能废弃标记、设计变更 |
| **docs/modules/** | 模块文档源 | 查阅模块详细信息时 | 模块状态更新 |

### 关键教训

1. **绝对不能从AGENTS.md的Open Items获取待办信息** - 那是PRD阶段的原始设计，很多已解决但未更新
2. **正确做法**：展示待办时，必须从MEMORY.md的"待办"部分获取
3. **PRD可能落后于实现** - 必须反向检查，不能假设PRD是最新的
4. **一次性穷极所有方面** - 评估缺陷时必须完整列出所有缺失项

## 检查清单（4层 × 47项）

### 第一层：状态同步（MEMORY ↔ AGENTS ↔ PRD S22）

| 优先级 | 检查项 | 方法 | 输出 |
|--------|--------|------|------|
| P0 | AGENTS.md Open Items 是否与 MEMORY.md 一致 | 逐条比对两个文件的任务列表 | 一致/不一致列表 |
| P0 | PRD [S22] 状态是否与 MEMORY.md 一致 | 逐条比对 PRD 开放问题与 MEMORY.md | 一致/不一致列表 |
| P0 | MEMORY.md 待办是否标记最新状态 | 检查待办部分的日期和状态 | 最新状态确认 |
| P1 | 是否有过期文档需要标记 | 检查 docs/archive/ 目录 | 过期文档列表 |
| P1 | 经验教训是否需要更新 | 检查 AGENTS.md 教训记录 | 需要更新的教训 |

### 第二层：设计同步（PRD ↔ 实际实现）

| 优先级 | 检查项 | 方法 | 输出 |
|--------|--------|------|------|
| P0 | PRD 中描述的功能是否已实现 | 对比 PRD 功能列表与实际代码 | 未实现功能列表 |
| P0 | 已删除的功能是否在 PRD 中标记为废弃 | 检查 PRD 中是否有 [已废弃] 标记 | 废弃标记列表 |
| P0 | PRD 中的页面清单是否与实际路由一致 | 对比 PRD 页面清单与 `Get-ChildItem -Path "src/app" -Recurse -Filter "page.tsx"` | 一致/不一致列表 |
| P0 | PRD 中的数据模型是否与 Sanity schema 一致 | 对比 PRD 数据模型与 `Get-ChildItem -Path "sanity/schemas" -Filter "*.ts"` | 一致/不一致列表 |
| P1 | PRD 中的导航栏设计是否与 Navbar.tsx 一致 | 对比 PRD 导航栏描述与 `megaMenuItems` 数组 | 一致/不一致列表 |
| P1 | PRD 中的技术栈是否与 package.json 一致 | 对比 PRD 技术栈与 `package.json` 依赖 | 一致/不一致列表 |
| P1 | PRD 设计规范是否与 globals.css 一致 | 对比 PRD [S9] 颜色/字体/间距与 CSS 变量 | 一致/不一致列表 |
| P1 | PRD API 设计是否与实际路由一致 | 对比 PRD [S18] 与 `src/app/api/` 目录 | 一致/不一致列表 |
| P2 | PRD 安全要求是否与代码一致 | 对比 PRD [S2.5] 与 CSP/RLS/输入验证代码 | 一致/不一致列表 |
| P2 | PRD 无障碍要求是否与代码一致 | 对比 PRD [S19] 与组件 ARIA 属性 | 一致/不一致列表 |

### 第三层：内容完整性（i18n / Sanity / 组件）

| 优先级 | 检查项 | 方法 | 输出 |
|--------|--------|------|------|
| P0 | en.json/zh.json 的 key 是否对齐 | 解析两个文件，对比 key 列表 | 缺失 key 列表 |
| P0 | i18n 中定义的行业是否完整 | 检查 `home.industries` 是否包含6个行业 | 缺失行业列表 |
| P0 | Sanity schema 字段是否在前端 query 中使用 | 解析 GROQ query，对比 schema 字段 | 未使用字段列表 |
| P0 | 组件 props 是否与 PRD 定义一致 | 解析组件 props，对比 PRD 数据模型 | 不一致字段列表 |
| P1 | i18n 中定义的产品是否与 Sanity 数据一致 | 对比 i18n `products` 与 Sanity 产品数据 | 不一致产品列表 |
| P1 | i18n 中定义的解决方案是否与 Sanity 数据一致 | 对比 i18n `solutions` 与 Sanity 解决方案数据 | 不一致方案列表 |
| P1 | 组件使用的 i18n key 是否存在 | 解析组件 `t()` 调用，对比 en.json | 缺失 key 列表 |
| P1 | API 端点是否与 PRD [S18] 一致 | 对比 `/api/*` 路由与 PRD API 设计 | 不一致端点列表 |
| P2 | globals.css 设计 token 是否与 PRD [S9] 一致 | 解析 CSS 变量，对比 PRD 设计规范 | 不一致 token 列表 |
| P2 | Sanity coverImage 格式是否正确 | 检查 coverImage 字段格式 | 格式错误列表 |

### 第四层：文档间一致性

| 优先级 | 检查项 | 方法 | 输出 |
|--------|--------|------|------|
| P1 | MEMORY.md 变更记录是否完整 | 检查变更记录是否有遗漏 | 遗漏记录列表 |
| P1 | AGENTS.md 规则是否与实际开发流程一致 | 对比规则与实际代码 | 不一致规则列表 |
| P1 | Hook 与 Skill 逻辑是否一致 | 对比 Hook 代码与 Skill 检查清单 | 不一致项列表 |
| P2 | docs/modules/ 目录文档是否需要更新 | 读取模块文档，检查内容是否过期 | 需要更新的文档 |
| P2 | CHANGELOG.md 是否存在且更新 | 检查文件是否存在 | 文件状态 |
| P2 | README.md 内容是否与项目一致 | 对比 README 与实际项目结构 | 不一致项列表 |

## 触发条件

### 自动触发（Hook）

| 触发时机 | 检查范围 | 说明 |
|----------|----------|------|
| `tool.execute.after` (edit/write) | 变更的文件相关检查 | 只检查本次修改的文件 |
| `tool.execute.after` (bash) | 全量检查 | bash 可能修改任意文件 |
| task done | 全量检查 | 完成后确认所有状态同步 |

### 手动触发（Skill）

| 触发时机 | 检查范围 | 说明 |
|----------|----------|------|
| 用户要求 "doc-sync" | 全量检查 | 执行完整的4层检查 |
| Session 结束前 | 状态同步 | 只检查第一层 |
| 功能删除后 | 设计同步 + PRD 更新 | 检查第二层并更新 PRD |
| 新功能实现后 | 设计同步 | 检查第二层 |

### 触发条件选择

```
如果 变更类型 == "i18n文件":
    执行 第三层（i18n检查）
如果 变更类型 == "Sanity数据":
    执行 第三层（Sanity检查）
如果 变更类型 == "组件文件":
    执行 第二层（设计同步）+ 第三层（内容完整性）
如果 变更类型 == "文档文件":
    执行 第四层（文档间一致性）
如果 变更类型 == "任意":
    执行 全量检查
```

## 执行流程

### 标准流程（12步）

```
1. 读取 MEMORY.md → 获取当前状态
2. 读取 AGENTS.md Open Items → 逐条比对
3. 读取 PRD [S22] → 逐条比对
4. 读取 PRD 页面清单（约第510-525行）→ 对比实际路由
5. 读取 PRD 数据模型（约第435-445行）→ 对比 Sanity schema
6. 读取 PRD 导航栏设计（约第274-280行）→ 对比 Navbar.tsx
7. 解析 en.json/zh.json → 检查 key 对齐
8. 解析 Sanity schema → 检查字段与前端 query 一致性
9. 解析组件 props → 检查与 PRD 定义一致性
10. 标记所有差异 → 输出同步报告
11. 执行修复 → 更新文档
12. 验证修复 → 重新检查确认
```

### 增量流程（针对单文件变更）

```
1. 识别变更文件类型
2. 根据触发条件选择检查范围
3. 只执行相关检查项
4. 输出差异报告
5. 执行修复
6. 验证修复
```

## 验证机制

### 修复后验证

```
1. 执行修复 → 更新文档
2. 重新执行检查 → 确认修复生效
3. 如果检查通过 → 标记为已修复
4. 如果检查失败 → 标记为修复失败，重新分析
```

### 验证规则

| 修复类型 | 验证方法 |
|----------|----------|
| PRD 更新 | 重新读取 PRD，确认内容已更新 |
| i18n 更新 | 重新解析 en.json/zh.json，确认 key 对齐 |
| 组件更新 | 重新读取组件代码，确认 props 一致 |
| 代码更新 | 运行 `npm run lint && npx tsc --noEmit && npx next build --webpack` |

## 常见错误避免

| 错误 | 正确做法 |
|------|----------|
| 从 AGENTS.md 获取待办 | 从 MEMORY.md 获取待办 |
| 从 PRD 获取当前状态 | 从 MEMORY.md 获取当前状态 |
| 仅凭文件树判断实现状态 | 读取源代码确认实际内容 |
| 采信旧评估报告 | 以最新 session 记录为准 |
| 同步时只改"已完成"条目 | **逐条比对所有状态，包括已放弃/已降级/待确认** |
| 只同步状态不同步设计 | **功能删除/新增必须同步更新 PRD 设计规范** |
| 假设 PRD 是最新的 | **PRD 可能落后于实现，必须反向检查** |
| 评估只给笼统结论 | **必须完整列出所有具体缺失项** |
| 只做正向检查 | **必须反向检查 PRD 是否反映实现** |
| 分批输出结果 | **一次性穷极所有方面** |
| 修复后不验证 | **修复后必须重新检查确认** |
| 每次都全量检查 | **根据变更类型选择增量检查** |
