# TGWS文案修改最佳实践

## 核心原则

### 1. 品牌调性一致性
- **专业**：企业IT，不是初创公司
- **技术**：代码优先，基础设施聚焦
- **可靠**：信任信号，合作伙伴logo，案例研究
- **反模式**：不要渐变CTA、虚假指标、模板化卡片网格

### 2. 文案位置优先级
1. **Hero区域**（最重要）：用户首先看到
2. **导航和CTA**：影响用户行为
3. **产品描述**：影响转化率
4. **其他区域**：次要但重要

### 3. 修改原则
- **简洁性**：避免冗长、模板化的表达
- **具体性**：用具体描述替代泛泛形容词
- **一致性**：中英文版本同步修改
- **可测试性**：修改后运行npm run build验证

## 修改流程

### 1. 扫描阶段
- 使用`copy-writing-guide`工具扫描文案
- 识别包含AI化用词的文案
- 按优先级分类（Hero > 导航 > 产品 > 其他）

### 2. 评估阶段
- 分析每个文案的上下文
- 评估修改的风险（核心品牌信息 vs 次要文案）
- 确定修改的必要性

### 3. 修改阶段
- **低风险修改**（形容词替换）：可直接执行
- **高风险修改**（核心品牌信息）：需要用户确认
- 中英文版本同步修改
- 修改后运行`npm run build`验证

### 4. 验证阶段
- 检查编译是否通过
- 检查i18n是否正常
- 检查视觉效果是否受影响

## 特殊文案处理

### Hero标签（最重要）
- 需要简洁、专业、易记
- 与主标语配合
- 避免重复主标语的内容

### 产品描述
- 强调具体功能和 benefits
- 避免泛泛形容词
- 符合企业IT采购语言

### 转化标题
- 直接、有力
- 强调行动
- 避免过于泛泛

## 文档同步

### 修改后必须更新：
1. **MEMORY.md**：更新任务状态
2. **AGENTS.md**：如果修改了开发规则
3. **PRD**：如果修改了设计规范

### 文档职责划分：
- **MEMORY.md**：真实状态源
- **AGENTS.md**：规则约束源
- **PRD**：设计权威源

## 常见错误避免

1. **不要过度修改**：只修改真正有问题的文案
2. **不要改变核心信息**：保持品牌核心价值不变
3. **不要忽略上下文**：文案需要与周围内容协调
4. **不要忘记测试**：修改后必须验证编译和功能
5. **不要单独修改**：中英文版本必须同步
