# TGWS 访问者用途流水线分析

> 视角：**访问者**（不是代码结构，也不是产品功能清单）
> 问题：一个人带着某个目的进来，他实际会经过哪些环节？每个环节系统替他做了什么？哪一步在等哪一步？
> 方法：逐个路由 + 逐个 API 反推真实路径，只写代码能走通的；走不通的集中列在第 6 节。

---

## 0. 怎么读这份文档

"流水线"= **同一目的下，访问者动作与系统响应交替推进的一串环节**。每条流水线有：

- **入口**：他从哪儿进来（决定他带着什么预期）
- **环节序列**：动作 → 系统响应 → 产出物流向哪里
- **出口**：他最后停在哪儿（成交 / 自助解决 / 留资 / 流失）
- **与其他流水线的关系**：哪里汇流、哪里回流、哪里共享同一段管道

判读符号：`→` 顺序推进；`⇒` 条件分支；`⤴` 回流到另一条流水线；`⚠` 已确认的断裂点（详见第 6 节）。

## 1. 访问者分型与用途矩阵

| 类型 | 他是谁 | 核心问题 | 走的流水线 | 典型入口 |
|------|--------|----------|-----------|----------|
| **A 陌生人** | 搜索引擎/外链点进来 | "这家靠不靠谱？" | P1 认知 | `/blog/[slug]`、`/en` |
| **B 评估者** | 有项目，在选型 | "你能解决我的问题吗？" | P2 产品 → P3 方案 → P4 算账 | Navbar 产品/行业、首页三支柱卡 |
| **C 高意向** | 已决定要聊 | "怎么联系？" | P5 咨询 | 任意页 CTA、Footer |
| **D 说不清的人** | 只知道关键词 | "你们有没有 X？" | P6 搜索 | Navbar 搜索图标 |
| **E 现有客户（未登录）** | 出故障了 | "怎么修？" | P7 自助 → P8 报障 | `/help`、Navbar 支持 |
| **F 现有客户（已登录）** | 想知道进度 | "我的单到哪了？" | P9 跟踪 | `/support` |
| **G 账号持有人** | 要改资料 | "改下邮箱/密码" | P10 账号 | UserMenu → `/profile` |
| **H 内部管理员** | 不是访客，是承接方 | "哪些单要处理？" | P11 处置 | `/support/admin/dashboard` |

**关键结构事实：A→B→C 是一条漏斗；E→F 是另一条闭环；D 是漏斗的"侧门"；H 是漏斗末端的接收方。两条业务线（售前线索 / 售后工单）在数据层完全隔离，只在导航栏共享入口。**

## 2. P0 入场层：所有流水线的共同前置

任何人访问任何页面，都先过这 5 关。**这段是所有流水线的公共管道，它的耗时决定了后面每一步的耐心预算。**

| # | 系统动作 | 目的 | 访问者感知 | 实现位置 |
|---|----------|------|-----------|----------|
| 0.1 | 无语言前缀的 URL → 302 到 `/en` | 保证每个页面都有明确语言，SEO 不产生重复内容 | 几乎无感（一次跳转） | `app/page.tsx` |
| 0.2 | middleware 先跑 i18n 重写，再刷新 Supabase 会话，把新 cookie 合并回响应 | 语言路由与登录态在同一次请求里解决，避免二次往返 | 无感；已登录者不会莫名掉线 | `src/middleware.ts` + `lib/supabase/middleware.ts` |
| 0.3 | 首屏 HTML 里同步执行主题脚本：读 localStorage → 加 `.dark` | 避免"先白后黑"的闪烁 | 看到的就是他上次选的主题 | `[locale]/layout.tsx` 内联脚本 |
| 0.4 | 字体 preload + 两个 preconnect（在线字体站、Sanity CDN） | 让标题字体不出现"字体跳动" | 文字很快定型 | `[locale]/layout.tsx` `<head>` |
| 0.5 | 挂 Navbar（固定玻璃态）+ Footer + Cookie 横幅 + 回顶按钮 | 全站一致的外壳与合规提示 | 导航常在，不被滚动带走 | `[locale]/layout.tsx` |

**分支：内容页 vs 交互页的首屏差异（直接影响体验，值得单列）**

| 页面类型 | 首屏怎么来 | 访问者感受 |
|----------|-----------|-----------|
| 产品/博客/方案/关于 | 服务端已渲染好（ISR 缓存 1 小时） | 秒开，断网也能看 |
| **首页、/help、/compare、/vmware-alternative、/contact、/support** | **整页 `'use client'`，内容靠 JS + i18n JSON 渲染** | 首屏要等 JS 执行；弱网/低端机上会先看到空白或骨架 |

> 这不是 bug，是取舍：这些页面要交互（Tab、计算器、表单），但代价是"最贵的首页"反而没有服务端直出。

## 3. 售前漏斗：A → B → C

### P1 认知流水线（陌生人 → 读者 → 潜在客户）

**入口**：搜索引擎结果、LinkedIn/WhatsApp 外链、直接访问首页。

| # | 访问者动作 | 系统响应 | 这一步的目的 | 依赖 |
|---|-----------|----------|-------------|------|
| 1.1 | 点进 `/blog/[slug]` 或 `/en` | ISR 命中缓存直接返回；未知 locale 直接 404 | 3 秒内给出"这家讲得专业"的判断依据 | P0 |
| 1.2 | 扫读标题/摘要/封面 | 封面图三态兜底（对象/URL/缺失都有方案），OG 图保证分享卡片不裂 | 不因为一张图挂掉而丢掉信任 | 1.1 |
| 1.3 | 读正文 | `article-content` 排版（标题层级、引用、代码、列表统一）；架构图作为内嵌 SVG | 让技术读者能读下去 | 1.2 |
| 1.4 | 读到末尾 | 正文下方固定一块 CTA → `/contact` | 把"读完了"这个最高注意力时刻转成动作 | 1.3 |
| 1.5 | 抬头看导航 | Navbar 常驻：产品 / 方案 / 博客 / 关于 / 支持 + 搜索 + 语言 + 主题 | 给他下一步的岔路口 | 全程 |

**出口**：⤴ P2（点产品）、⤴ P3（点方案）、⤴ P5（点 CTA）、离开。

**这条流水线的缺失**：文末**没有相关文章推荐**。技术读者读完一篇想继续读第二篇，只能回列表页重找 —— 这是最容易补、收益最直接的转化损失。

---

### P2 产品评估流水线（评估者 → 缩小到 1–2 个候选）

**入口**：Navbar 产品菜单（三支柱）、首页三支柱卡、博客内链、搜索结果的 product 类型。

| # | 访问者动作 | 系统响应 | 目的 | 依赖 |
|---|-----------|----------|------|------|
| 2.1 | 进 `/products` | 一次 GROQ 拉全量（category + order 排序），客户端渲染 | 先给他"能力全景" | P0 |
| 2.2 | 按支柱分流 | `/products/build` `/run` `/protect`：服务端取数 → 客户端按 `category` 过滤 | 三个词就是他的自我分类 | 2.1 |
| 2.3 | 在 Run 里找虚拟化 | Run 额外按 `runSubgroups`（虚拟化/HCI/云平台/硬件/托管/BCDR/路由交换/无线）分组；并在"基础设施"组插入一张 **VMware 替代方案专题卡** | 把"最高需求的迁移话题"提到和其他产品平级的位置 | 2.2 |
| 2.4 | 点开某产品 | `/products/[slug]`：服务端取详情 + 注入 Product JSON-LD + 面包屑 | 详情页同时服务人和搜索引擎 | 2.3 |
| 2.5 | 看特性列表 | 优先用 i18n 的 `features.{slug}`，缺失才回退 Sanity 的 `features[]` | 让文案可精修，又不至于空着 | 2.4 |

**出口**：⤴ P4（从 Run 的专题卡去算 TCO）、⤴ P5（详情页 CTA）、⤴ P1（回博客）、离开。

**这条流水线的结构性依赖**：产品 slug 到文案/图标的映射写在 `products/shared.tsx` 的两个常量表里（`slugToI18n`、`productIcons`），**新增一个产品必须同时改这两张表 + Sanity + i18n JSON**，漏一处就会出现"标题是 key 原文"或"图标空白"。

---

### P3 方案匹配流水线（评估者 → "你懂我这个行业"）

**入口**：Navbar 行业子菜单（6 个）、Footer 行业列、搜索结果 solution 类型。

| # | 访问者动作 | 系统响应 | 目的 | 依赖 |
|---|-----------|----------|------|------|
| 3.1 | 点 ` healthcare` | `/solutions?tab=healthcare` —— **Tab 由 query 参数驱动** | 链接可分享、可被搜索直达、可回退 | P0 |
| 3.2 | 看行业卡 | 每行业固定四段：痛点（challenges）→ 对应方案（solutions）→ 推荐产品（recommendedProducts）→ 一个指标（metricLabel） | 用"你行业的语言"复述他的问题 | 3.1 |
| 3.3 | 点推荐产品 | 跳 `/products/[slug]` | 把行业叙事落回具体可采购物 | 3.2 |

**出口**：⤴ P2、⤴ P5。

**顺序上的巧思**：先"痛点"再"方案"再"产品"，是**共情 → 解法 → 报价物**的经典说服顺序，不是按数据库字段顺序排的。

---

### P4 自算 TCO 流水线（评估者 → 高意向，全站最深的一条）

**入口**：`/vmware-alternative`、首页两处 CTA（含 `#tco-calculator` 锚点）、Footer "TCO Calculator"、P2 的 Run 专题卡。

| # | 访问者动作 | 系统响应 | 目的 | 依赖 |
|---|-----------|----------|------|------|
| 4.1 | 进替代方案页 | 客户端渲染：5 家方案（Proxmox/Sangfor/Nutanix/StarWind/Huawei）→ 4 步迁移路径 → 4 个理由 → 数据条 | 先解决"敢不敢换"的心理问题 | P0 |
| 4.2 | 点"计算你的 TCO" | 锚点滚到 `#tco-calculator`，`TcoCalculatorSection` 发起 `GET /api/tco`（**force-dynamic，不吃缓存**） | 拿到的永远是最新报价配置 | 4.1 |
| 4.3 | 等配置返回 | 三种态：加载中转圈 / 失败显示"暂不可用" / 成功渲染计算器 | 配置挂了也不白屏 | 4.2 |
| 4.4 | 输入核数 / CPU 数 / 年数 | 纯前端 `useMemo` 计算，**不发请求** | 零延迟、零隐私顾虑 | 4.3 |
| 4.5 | 点"计算" | 按场景（scenario）算 3 家 bundle：订阅制 = 单价×总核数×年；买断制 = 单价×CPU + 单价×费率×年×CPU；结果按总价升序 | 让"贵不贵"变成可比较的三个数字 | 4.4 |
| 4.6 | 看逐年累计 | `calcCumulative` 逐年重算，前端手绘 SVG 折线 | 让"第 3 年反超"这类结论自己浮出来 | 4.5 |
| 4.7 | 导出 | `XMLSerializer` 取 SVG → Blob → canvas → PNG 下载，文件名 `tco-comparison.png` | 他可以拿去给老板/客户看 | 4.6 |
| 4.8 | 看底部 | 免责声明 + `lastUpdated` + CTA → `/contact` | 交代"数字是估算，细节来聊" | 全程 |

**出口**：⤴ P5（点 CTA）、带走一张 PNG 后离开。

**这条流水线的设计意图很清楚**：用"你自己算一遍"消除价格不信任。但它有一个刻意的（也可能是疏忽的）缺口 —— **算完不要求留邮箱**。高意向用户的最强信号（认真填了核数、导出了图）没有被记录下来，转化只能靠他自己点 CTA。

### P5 主动咨询流水线（高意向 → 线索入库）

**入口**：Navbar "Contact"、首页底部 CTA、各页 CTA、博客文末 CTA、TCO 页 CTA。

| # | 访问者动作 | 系统响应 | 目的 | 依赖 |
|---|-----------|----------|------|------|
| 5.1 | 进 `/contact` | 客户端表单（姓名*/邮箱*/公司/电话/留言*）+ 右侧办公室、地图、社交、WhatsApp 二维码 | 一屏之内给全"其他联系方式"，降低只填表的压力 | P0 |
| 5.2 | 填错 | 前端即时校验：必填 + 邮箱正则，`aria-invalid` + `role="alert"` | 不让他在提交后才知道错 | 5.1 |
| 5.3 | 提交 | `POST /api/contact`：同源校验（Origin 白名单）→ 限流 5 次/分钟 → 字段长度校验 | 挡机器人和跨站提交 | 5.2 |
| 5.4 | 服务端处理 | **先**写 Supabase `contact_submissions`；**再**调 Odoo 建 `crm.lead` | 保证"线索一定不丢"，CRM 只是增强 | 5.3 |
| 5.5 | Odoo 失败 | 只记一条结构化错误日志，**接口仍返回成功** | 不让 CRM 故障毁掉一次真实咨询 | 5.4 |
| 5.6 | 回到页面 | 绿色成功条（`aria-live`），表单清空 | 明确告诉他"收到了" | 5.5 |

**出口**：结束（等待人工跟进）。

**两个不对称，必须指出**：
1. **客户收不到任何确认邮件**。`sendTicketCreatedEmail` / `sendTicketStatusEmail` 都给了工单客户，唯独联系表单没有给客户回执。他填完只看到一行绿字，关掉页面后没有任何凭证。
2. **表单不采集"他对什么感兴趣"**。销售拿到的只有一段自由文本留言，无法按产品线分派。

## 4. 侧门与自助：D、E 两条线

### P6 模糊探索流水线（说不清需求 → 搜索 → 要么被接住，要么变成线索）

这是全站**唯一会承认"我们没有"**的地方，也是唯一把"没有"转成销售机会的地方。

**入口**：Navbar 搜索图标（桌面/移动都在）。

| # | 访问者动作 | 系统响应 | 目的 | 依赖 |
|---|-----------|----------|------|------|
| 6.1 | 点开搜索 | 模态弹出、自动聚焦、筛选面板直接展开 | 减少一次点击 | P0 |
| 6.2 | 还没输入 | 拉 Sanity 最新 3 产品 + 2 方案 + 2 博客，并在最前面**硬插一张 VMware 替代方案卡** | 用"最近更新"制造内容活跃感，同时把战略话题顶到第一 | 6.1 |
| 6.3 | 输入关键词 | 防抖后 `POST /api/search`（限流 20 次/分钟） | 控制对外部付费 API 的消耗 | 6.2 |
| 6.4 | 服务端并行 | 三路同时跑：Sanity 站内（含中英关键词映射，如"超融合→hci"）／Google CSE／Tavily（自动注入公司业务上下文） | 一次请求拿到"我们有的 + 世界上有的" | 6.3 |
| 6.5 | 结果处理 | 按 URL 去重 → 19 个低质/竞品域名黑名单 → 广告词过滤 | 不让站外垃圾结果污染品牌 | 6.4 |
| 6.6 | 生成摘要 | Gemini 2.0 Flash 强制输出三段 `[RESOURCES]/[INSIGHT]/[SOURCES]`；缺段自动补、越界域名自动删；无 key 则模板拼接 | 保证"AI 摘要"永远有三段、永远不引用垃圾站 | 6.5 |
| 6.7 | 判定缺口 | 站内命中 ≤2 条且不是"about/contact"这类通用词 → 判定为**能力缺口** | 把"搜不到"从失败变成情报 | 6.6 |
| 6.8a | 有结果 | 分三栏展示：站内资源 / AI 摘要 / 站外参考，点站内结果进对应页面 | ⤴ P1、P2、P3 | 6.7 |
| 6.8b | 判定缺口 | 展示留资表单 → `POST /api/search/lead`（限流 3 次/分钟）→ 写 Supabase `leads` | 把"我们暂时没有"变成一条可跟进的销售线索 | 6.7 |
| 6.9 | 留资之后 | Resend 发 **4 封**：管理层、销售、技术各一封内部通知 + 客户一封确认（承诺 48 小时） | 内部三方同时知情；客户拿到承诺 | 6.8b |
| 6.10 | 搜索日志 | 写一条 Sanity `searchLog`（查询词、结果数、是否缺口） | 为内容选题提供依据 | 全程 |

**出口**：⤴ P1/P2/P3、留资结束、离开。

**这条流水线的价值排序**：6.8b 的缺口留资 > 6.8a 的正常导流。因为"搜了但你没有"是最诚实的购买信号。

### P7 自助排障流水线（现有客户 → 能自己解决就不建单）

**入口**：Navbar 支持菜单里的 FAQ、Footer "FAQ"、搜索结果 faq 类型（⚠ 实际指向 `/help`）。

| # | 访问者动作 | 系统响应 | 目的 | 依赖 |
|---|-----------|----------|------|------|
| 7.1 | 进 `/help` | 客户端渲染：分类（全部/产品/技术/账户/账单）+ 搜索框 + 折叠问答 | 先让他自己找，减少工单量 | P0 |
| 7.2 | 输入关键词 | **纯前端字符串过滤**（不走 `/api/search`、不查 CMS） | 零延迟、零成本 | 7.1 |
| 7.3 | 点开某条 | Accordion 展开；同时整页注入 FAQ JSON-LD | 内容既给人看，也给搜索引擎看 | 7.2 |
| 7.4a | 解决了 | 结束（可能去看别的，或离开） | 工单被省下来 | 7.3 |
| 7.4b | 没解决 | 页面无"仍然需要帮助 → 提单"的显式按钮，需自己从 Navbar 摸到 `/support` | ⚠ 断点：自助失败后没有下一步指引 | 7.3 |

**这条流水线的隐藏成本**：FAQ 内容**不在 CMS 里**，而是按 `faqCounts` 循环拼 i18n key 从 JSON 读。运营想加一条问答，必须改代码发版。Sanity 里那个 `faq` schema 目前没人用。

## 5. 售后闭环：E/F/G 与内部 H

### P8 身份建立流水线（新客户注册 → 邮箱验证 → 可用账号）

**入口**：`/support/login` 底部"Create account"、Navbar 支持菜单、P7 的 7.4b 之后。

| # | 访问者动作 | 系统响应 | 目的 | 依赖 |
|---|-----------|----------|------|------|
| 8.1 | 点进 `/support/register` | **服务端**先跑 `redirectIfAuthenticated()`：已登录直接踢回 `/support` | 不让已登录用户看到无意义的注册页 | P0 |
| 8.2 | 填表 | 前端校验：两次密码一致、长度、邮箱格式 | 减少无效注册 | 8.1 |
| 8.3 | 提交 | `supabase.auth.signUp()`，`emailRedirectTo` 指向 `/api/auth/callback` | 把"验证"和"建会话"合并成一次点击 | 8.2 |
| 8.4 | 成功 | **停在原地**，显示"验证邮件已发送至 xxx"，**不跳转** | 明确告诉他"去邮箱点链接"，避免他以为没成功而重复注册 | 8.3 |
| 8.5 | 点邮件链接 | `/api/auth/callback`：code 换 session；`next` 参数做防开放重定向（含 decode 二次校验） | 一次点击完成验证 + 登录 | 8.4 |
| 8.6 | 落地 | 重定向到 `/support` | 直接进入他能用的界面 | 8.5 |

**Google OAuth 是同一入口**：登录页的 Google 按钮走 `signInWithOAuth`，回调同样是 `/api/auth/callback`，所以 8.5 之后的路径完全共用 —— 这是设计得比较干净的一处。

**⚠ 这条流水线下游有一个仓库层面看不到的环节**：注册只写 `auth.users`，**全仓库没有任何 `INSERT INTO public.users`，也没有 `handle_new_user` 触发器**。而 `tickets.user_id` 外键指向 `public.users(id)`。意味着按仓库代码，新注册用户**第一次建单会撞外键约束**。线上可能已手工建过触发器 —— 但这属于"仓库没记录、线上靠手工"的高风险状态，必须验证（详见第 6 节 R1）。

### P9 进度跟踪流水线（已登录客户 → 看单 → 然后卡住）

**入口**：登录后自动落到 `/support`；或 UserMenu → "Support"。

| # | 访问者动作 | 系统响应 | 目的 | 依赖 |
|---|-----------|----------|------|------|
| 9.1 | 进 `/support` | 客户端 `auth.getUser()`；无 session → **客户端** `router.push` 到登录页 | 兜住直接输 URL 的人 | P8 |
| 9.2 | 同时 | 查 `users.role` 判断是否管理员 → 拉 `/api/tickets` 拿自己全部工单 | 一次拿全，前端自己算统计 | 9.1 |
| 9.3 | 看默认 Tab（dashboard） | 4 张统计卡（总/待处理/处理中/已解决）+ 两个快捷入口 + 最近 3 条单 | 先给"我一共几张单、几张在等我" | 9.2 |
| 9.4 | 切 my-tickets | 完整列表：单号、主题、状态徽章、类别、时间；支持关键词过滤 | 定位到具体那张单 | 9.3 |
| 9.5 | 想看详情/对话/附件 | **没有详情页**。`/api/tickets/[id]` 存在但前端从不调用；`TicketList` import 了 `AttachmentPreview` 却没有渲染它 | ⚠ 断点：他能看到"有一张单"，看不到单里发生了什么 | 9.4 |
| 9.6 | 等进展 | 管理员改状态时，Resend 发状态变更邮件到他的注册邮箱（链接固定指 `/en/support`） | 唯一的进展通知渠道 | 全程 |

**出口**：离开（下次再来还是 9.3）。**没有站内回复入口**：`ticket_comments` 表只读不写，`sendTicketReplyEmail` 零调用 —— 客户要补充信息，只能新建一张工单。

**这条流水线的实质**：它是一个**只读看板**，不是工单对话系统。这一点对"现有客户体验"的伤害比任何 UI 细节都大。

### P10 账号管理流水线（边缘但真实）

**入口**：UserMenu 下拉 → Profile。

| # | 访问者动作 | 系统响应 | 目的 |
|---|-----------|----------|------|
| 10.1 | 进 `/profile` | 客户端取 `getUser()`，无 session 跳登录 | 兜底 |
| 10.2 | 改显示名 | `supabase.auth.updateUser({ data: { display_name } })`，写进 user metadata | 轻量、不需要额外表 |
| 10.3 | 改密码 | 校验两次一致 + ≥8 位 → `updateUser({ password })` | 自助改密 |
| 10.4 | 保存 | 成功提示（中英按 locale） | 明确反馈 |

**注意**：这里改的是 `auth.users` 的 metadata，**不是 `public.users.full_name`**。两处字段各存各的，会长期不一致。

**忘记密码**是另一个子路径：登录页 → 输邮箱 → 调 `resetPasswordForEmail`，但 `redirectTo` 指向 `/api/auth/reset-password`（一个只接受 POST 的接口）。⚠ 邮件链接点开大概率 405，而不是"设置新密码"界面。

### P11 内部处置流水线（承接方，决定前面所有线索/工单的归宿）

**入口**：管理员登录后从 UserMenu 或直接输 URL 进 `/support/admin/dashboard`。

| # | 内部动作 | 系统响应 | 目的 |
|---|---------|----------|------|
| 11.1 | 进管理台 | **服务端** `requireAdmin()`：未登录 → 登录页；非 admin/super_admin → 踢回 `/support` | 在客户端 bundle 加载前就拦住 |
| 11.2 | 看统计 | `GET /api/tickets/stats`：总数、按状态/类别/优先级分布、平均单龄、最近 5 条 | 一眼看清积压 |
| 11.3 | 想做点什么 | **页面上没有任何操作按钮** —— 这个看板是只读的 | ⚠ 断点：看得到，动不了 |

## 6. 流水线之间的关系网

### 6.1 汇流结构（谁最终流向谁）

```
P1 认知 ──┬──▶ P2 产品 ──┬──▶ P4 TCO ──┐
          │              │              │
          ├──▶ P3 方案 ──┘              ├──▶ P5 咨询 ──▶ [Supabase contact_submissions]
          │                             │                      └──▶ [Odoo crm.lead]
          └──▶ P6 搜索 ──┬──▶ 回 P1/P2/P3
                         └──▶ 缺口留资 ──▶ [Supabase leads] ──▶ 4 封邮件

P7 自助 ──▶ 解决（出口）
        └──▶ 未解决 ──▶ P8 注册 ──▶ P9 跟踪 ──▶ 等待 H 处置
                                        │
                                        └─ (无对话能力) ──▶ 再建一单
```

### 6.2 共享环节（改一处影响多条线）

| 共享环节 | 影响哪些流水线 | 一旦出问题 |
|----------|----------------|-----------|
| `middleware`（i18n + 会话） | **全部** | 全站语言错乱或登录态丢失 |
| Navbar（含搜索/语言/主题/用户菜单） | **全部** | 所有入口同时失效 |
| `api-guard`（同源 + 限流 + 字段校验） | P5、P6、P8、P9、P11 | 要么被刷，要么正常用户被误拦 |
| `logServiceError` | 全部服务端环节 | 出问题时无法定位，只能看到"失败" |
| i18n JSON（19 个命名空间） | 所有客户端页面 | 显示 key 原文，专业感受损 |
| Sanity Webhook → `/api/revalidate` | P1、P2、P3（内容新鲜度） | 内容改了 1 小时才生效，或永不生效 |

### 6.3 顺序上的三条硬依赖

1. **P8 必须在 P9 之前**：没有邮箱验证就没有 session，`/support` 的客户端守卫会把人推回登录页。
2. **P2/P3 的详情页必须在搜索/方案之后**：它们是所有导流的落点，404 会让前面所有环节白做。
3. **P11 必须在 P9 之后**：工单状态只能由管理端推进，客户端只是等待方。两者通过 `tickets.status` 单向传递，**没有站内通知通道，只能靠邮件**。

### 6.4 两条业务线的隔离（重要）

| 维度 | 售前线（P1–P6） | 售后线（P7–P11） |
|------|------------------|-------------------|
| 身份要求 | 完全匿名 | 强身份（邮箱验证） |
| 数据落地 | `contact_submissions`、`leads` | `tickets` + 4 张关联表 |
| 通知 | 仅 P6 缺口留资会给客户发信 | 建单/改状态发信 |
| 承接方 | 销售/Odoo | 管理员看板 |
| 共用 | Navbar、Footer、i18n、错误日志、限流器 —— 仅此而已 | 同左 |

**结论：两条线在代码里几乎没有耦合。** 好处是互不影响；代价是**同一个客户在售前聊过、售后报障时，系统不认为他们是同一个人**（`leads` 与 `users` 无关联字段）。

## 7. 从访问者视角看的体验断点（按影响排序）

| ID | 断点 | 访问者感受 | 证据 | 影响面 |
|----|------|-----------|------|--------|
| **R1** | 注册后 `public.users` 无记录，工单外键可能直接失败 | "注册成功了，但提不出去单" | 全仓库无 `INSERT INTO users` / `handle_new_user` trigger；`tickets.user_id REFERENCES users(id)` | P8→P9 全断（**需线上验证是否手工补过**） |
| **R2** | 工单没有详情页、没有对话、没有回复 | "我只看到一张单的标题，永远不知道里面说了什么" | `/api/tickets/[id]` 前端零调用；`ticket_comments` 只读；`sendTicketReplyEmail` 零调用 | P9 实质降级为只读列表 |
| **R3** | 附件预览组件被 import 但没有渲染 | "我传的截图去哪了？" | `AttachmentPreview` 在 `TicketList.tsx` 仅出现 1 次（import 行） | P8 上传的价值无法被确认 |
| **R4** | 密码重置链接指向 POST-only API | "点邮件里的链接，报错了" | `LoginForm` `redirectTo: /api/auth/reset-password`；该路由只有 POST | P10 自助恢复失败 |
| **R5** | 管理台只读，操作藏在客户视图 | 内部："看得到积压，改不了" | admin dashboard 仅一处 `fetch(GET)`，无按钮 | P11 效率 |
| **R6** | 联系表单不给客户回执 | "我填完了，但没有任何凭证" | `/api/contact` 只写库 + Odoo，无 Resend 调用 | P5 信任 |
| **R7** | TCO 算完不留资 | 访客走了，销售不知道 | 计算与导出全在前端，无埋点提交 | P4 转化 |
| **R8** | 自助失败后无"去提单"按钮 | "FAQ 没解决，然后呢？" | `/help` 无指向 `/support` 的 CTA | P7→P8 漏斗断 |
| **R9** | 博客无相关文章 | "看完一篇，没得看了" | `BlogDetail` 只有文末 CTA | P1 停留时长 |
| **R10** | 状态邮件链接固定 `/en/support` | 中文用户被丢到英文页 | `resend.ts` 中 `SITE_URL/en/support` 硬编码 | P9 细节 |
| **R11** | FAQ / Partner 有 CMS schema 但读的是代码 | 运营："改了没生效"（因为改错地方） | `/help` 走 i18n；首页 partners 硬编码 | P7、P1 |

## 8. 一条容易被忽略的流水线：内容供给（P12）

它不属于"访问者"，但**决定了 P1–P3 能提供什么**，所以必须记一笔。

```
运营/编辑
  → 在 Sanity Studio 改内容（或跑 151 个脚本批量入库）
  → 发布
  → Sanity Webhook 带上 _type 打到 /api/revalidate
  → 校验 secret（恒定时比较）
  → 按 _type 映射到受影响的路径（post→blog，product→products，solution→solutions…）
  → revalidatePath（精确路径）+ revalidateTag（类型级）
  → 下一次访问者请求命中新缓存
```

**这条链的脆弱点**：如果 Webhook 没配或 secret 不匹配，访问者最长要等 **1 小时**（`revalidate = 3600`）才能看到新内容；而运营会以为"我发了他就能看到"。`WEBHOOK-SETUP.md` 存在，说明这件事需要人工配置，不在代码里自动保证。

## 9. 一页总结

| 流水线 | 入口 | 关键环节数 | 终点 | 现状 |
|--------|------|-----------|------|------|
| P0 入场 | 任意 URL | 5 | — | 稳 |
| P1 认知 | 搜索/外链 | 5 | 转 P2/P3/P5 | 通，缺"下一篇" |
| P2 产品 | 导航/首页 | 5 | 转 P4/P5 | 通，靠两张常量表同步 |
| P3 方案 | 行业菜单 | 3 | 转 P2/P5 | 通 |
| P4 TCO | 专题页/首页 CTA | 8 | 转 P5 或带走 PNG | 通，无留资 |
| P5 咨询 | 全站 CTA | 6 | 线索入库 | 通，客户无回执 |
| P6 搜索 | 搜索图标 | 10 | 导流或缺口留资 | 通，唯一"承认没有"的出口 |
| P7 自助 | Help | 4 | 解决或转 P8 | 通，缺转出按钮 |
| P8 注册 | 登录页 | 6 | 进 P9 | **链路存疑（R1）** |
| P9 跟踪 | /support | 6 | 等待 H | **只读，无对话（R2/R3）** |
| P10 账号 | UserMenu | 4 | 完成 | 改密通，找回密码断 |
| P11 处置 | 管理台 | 5 | 推进工单 | **看板只读，操作在别处** |
| P12 内容供给 | Studio/脚本 | 6 | 影响 P1–P3 | 依赖 Webhook 人工配置 |

**一句话**：售前四条线（P1–P4）设计得相当完整，甚至比多数 B2B 站点更细（能力缺口检测、TCO 自算、行业四段叙事）；**售后线（P8–P11）只完成了"能提交"，没完成"能对话"**——这是当前访问者体验里落差最大的一段。
