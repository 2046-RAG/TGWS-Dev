## 1. 为什么要修

`003_add_search_tables.sql:50-51` 写了一条引用不存在列的策略：

```sql
CREATE POLICY "Users can view own leads" ON leads
  FOR SELECT USING (auth.uid() = user_id OR assigned_to = auth.uid());
```

`leads` 表只有 `assigned_to`，没有 `user_id`。PostgreSQL 在这里报
`column "user_id" does not exist`，整段 003 回滚。

后果取决于 003 当时怎么跑的：

| 情况 | 结果 |
|------|------|
| 整段事务执行（Supabase SQL Editor 默认） | `leads`、`search_logs`、策略、触发器**全部不存在** → 线索提交接口会报 `relation does not exist` |
| 逐条执行 | `leads` 存在，但 `search_logs`、策略、触发器缺失 |

005 对两种情况都做了兜底：全部 `CREATE ... IF NOT EXISTS` + `DROP POLICY IF EXISTS` + `DROP TRIGGER IF EXISTS`。

## 6. 常见问题

**报 `policy "Users can view own leads" for relation "leads" already exists`**
说明 003 曾经部分成功，但 005 用了 `DROP POLICY IF EXISTS`，不应出现。若出现，说明跑的不是 005 全文。

**报 `relation "users" does not exist`**
`users` 表不在 `public` schema，或 001 未执行。先确认 001 已跑。

**报 `must be owner of table leads`**
当前角色不是表 owner。用 Supabase SQL Editor 的默认 `postgres` 角色，不要用 anon/service key 的连接。

**跑完 005 后线索接口仍 500**
检查 API 日志里的具体错误；若为 `permission denied for table leads`，确认策略已建且服务端用的是带用户 JWT 的 client（匿名提交走 `WITH CHECK (true)`）。

## 7. 回滚

005 只做"补齐 + 修正"，不回滚数据。若必须回滚策略：

```sql
DROP POLICY IF EXISTS "Users can view own leads" ON leads;
DROP POLICY IF EXISTS "Users can create leads" ON leads;
DROP POLICY IF EXISTS "Admins can update leads" ON leads;
DROP POLICY IF EXISTS "Users can view own search logs" ON search_logs;
DROP POLICY IF EXISTS "Users can create search logs" ON search_logs;
DROP POLICY IF EXISTS "Admins can view all search logs" ON search_logs;
```

回滚后 RLS 仍启用但无策略 = 全部拒绝（除 service role）。不建议在 Production 回滚到无策略状态。
